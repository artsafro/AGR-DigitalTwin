## 2. Что удалось раскрыть

`GeoAGR.mse` совпадает с ранее декодированным установленным загрузчиком.
Его цепочка: макрос → MSE → `GeoAGR.exe` с путём INI → выполнение текста
из clipboard через `execute`. Это не документированный файловый API.
Повторная расшифровка того же MSE не открыла бы основную логику.

`GeoAGR.exe` — native PE, не .NET. Статически обнаружены строки AutoIt и ресурс
`10/SCRIPT/0` размером **5 210 010 байт**, содержащий маркер AutoIt.
Структура контейнера найдена; содержимое SCRIPT **не декомпилировано**.
Поиск готового AutoIt-декомпилятора по именам в `Desktop\zavod` ничего не дал.
QuickBMS-рецепт MSE не применялся к другому формату наугад.
Сам EXE не запускался, clipboard не читался, активация не исследовалась.

Три DLL — обычные managed-сборки с читаемыми именами методов и сигнатурами.
Собственный `tools/assembly_inventory` читает PE/CLR-метаданные через
[Microsoft PEReader / GetMetadataReader](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata.pereaderextensions.getmetadatareader).
Он не использует `Assembly.Load`, не вызывает методы и не запускает конструкторы
исследуемых сборок. Это восстановление API, **не восстановление C# исходников
и не полный аудит IL**. В репозитории только наш анализатор, метаданные и выводы.

### MAX-28 — DelaunayCore.dll

Публичный статический метод:

```text
DelaunayCore.Triangulator.ProcessAllFaces(
  Double[] allVertsXYZ, Int32[] facesVertsCount,
  Int32[] facesVertsFlat, Double[] facesNormalsAndCentersFlat
) -> Int32[]
```

Названия внутренних методов включают `InCircle`, `IsPointInPolygon`,
`SegmentsIntersect`, `ProcessAndAddGlobalEdge`. Кандидат для триангуляции
полигонов/подготовки Ground и UCX: DT-030/033. Возврат, судя по именам,
может описывать рёбра, а не треугольники — **семантика ещё не проверена**.
До адаптера установить базу индексов, упаковку normal/center, ориентацию и
поведение на вогнутой/неплоской грани, отверстии и вырожденных точках.
Решение: **изучить на тестовой сцене**, статус **prototype**.

### MAX-29 — FastFaceFinder.dll

```text
FastFaceFinder.FindOverlaps(
  Double[] flatTriVerts, Int32[] triOrigFaceIDs, Double[] flatTriBoxes,
  Int32[] flatTriVertIDs, Double[] flatTriNormals
) -> Boolean[]
```

Внутри есть `CoplanarTrianglesOverlap`, `EdgeIntersectsTriangle`,
`PointInTriangle2D`, структуры `CellKey`/`Vec3`. Это кандидат для проверки
перекрывающихся граней DT-020/021 перед экспортом. Тип результата известен;
соответствие его индексов исходным граням и численные допуски неизвестны.
Проверка: соседние грани с общим ребром, точный дубль, частичный coplanar overlap,
разные высоты, противоположные normals, большие координаты, вырожденная грань.
Решение: **изучить на тестовой сцене**, статус **prototype**.

### MAX-30 — moveall.dll

```text
FastCollisionSolver.SolveCollisions(
  Double[] sVertPositions, Int32[] sEdgeVerts,
  Double[] lVertPositions, Int32[] lFaceVerts, Int32[] lFaceCounts,
  Double[] lNormals, Double[] lBoxes,
  Double targetGap, Double offsetX, Double offsetY, Double offsetZ,
  Int32 p1, Int32 p2, Int32 p3, Int32 p4, Int32 p5
) -> Double[]
```

Имена `AddTriangleToVoxelGrid`, `LargeFaceCache`, `TriangulateDelaunay2D`
указывают на геометрический решатель. Предполагаемая связь: DT-030/033,
коррекция пересечений и зазоров. Значение **p1–p5 неизвестно**, поэтому делать
вызов с выдуманными флагами нельзя. Не выяснено, содержит результат координаты,
смещения или иной массив. Решение: **изучить на тестовой сцене**, **prototype**.

У всех трёх DLL assembly version `0.0.0.0`, зависимости `mscorlib 4.0.0.0`,
у первых двух также `System.Core 4.0.0.0`. Ссылок на Autodesk API в метаданных
не найдено: возможен отдельный вычислительный worker. Совместимость runtime,
лицензия на повторное использование и фактические вызовы из GeoAGR не доказаны.
Отсутствие подозрительных имён не заменяет проверку поведения кода.

## 3. Проверенные файловые интерфейсы

### GEN-11 — ucx_check.exe: полезный кандидат для адаптера

Строки бинарника и тестовый запуск указывают на CGAL 6.2 / AABB и собственный
OBJ parser. Исходников в поставке не найдено. Проверенный вызов:

```text
ucx_check.exe <абсолютный-путь-к-копии.obj> --quiet
```

Рядом с OBJ создаются одноимённые `.txt` (имена проблемных объектов) и `.log`.
`--quiet` не подавляет весь stdout. Код возврата 0 означает успешное выполнение,
**в том числе при найденных пересечениях**. Пустой `.txt` нельзя получать
путём подстановки отсутствующего файла: это разные состояния.

Пять новых тестов, только синтетические кубы в отдельных временных папках:

- Разнесённые кубы: exit 0, существует пустой `.txt`.
- Частично пересекающиеся кубы: exit 0, два ожидаемых имени в `.txt`.
- Куб целиком внутри другого: exit 0, пустой `.txt` — **вложенность пропущена**.
- Касание по общей грани: exit 0, два имени в `.txt` — трактуется как finding.
- Некорректный OBJ: exit 1, `.txt` отсутствует; появился `.log`.

Входы во всех случаях побайтово сохранены, результаты прочитаны повторно.
`.txt` содержит набор имён, не граф проблемных пар; реальные кириллические
имена и нестандартные варианты OBJ ещё не проверены. Сохранённый harness
проверяет положительный/отрицательный результат и неизменность входов.

Решение: **обернуть адаптером**, статус **prototype**. Для DT-021/033 это
существующий частичный detector пересечений поверхностей, не полный валидатор
UCX: нет доказательства проверки convexity, closure, coverage, проходов,
количества полигонов и нормативного зазора. Вложенность проверять отдельно.
Трактовку касания сверять с PDF36–37 и ADR-0002, не наследовать из exit code.

Адаптер должен экспортировать копию OBJ с устойчивыми object IDs в job-папку,
фиксировать hash EXE, ограничить время, проверить exit + наличие/свежесть `.txt`,
сопоставить имена и вернуть native findings. После изменения геометрии или
экспорта FBX проверку повторять по фактическому результату.

### GEN-12 — uvdilate.exe: RGB padding с потерей alpha

`--help` и реальный вызов подтвердили:

```text
uvdilate.exe -j=1 -o=<отдельный-output.png> <input.png>
```

Без `-o` утилита по умолчанию перезаписывает вход. Указания радиуса padding
в показанном CLI нет. Синтетическая RGBA16×16 с непрозрачным цветным квадратом
4×4 обработана успешно: на выходе **RGB16×16**, центр и угол равны RGB(37,113,211).
Alpha исчезла, заливка дошла до угла. Эти размеры/цвет — только тестовая фикстура.
Входной RGB PNG отклонён: exit 1, output отсутствует. Оба исходника сохранены.

Решение: **доработать обвязку**, статус **prototype**, DT-012/013.
Нельзя считать его готовым нормативным padding-алгоритмом или применять напрямую
к прозрачной растительности. Возможный workflow: сохранить исходный alpha/mask,
разделить острова, заполнить только согласованный радиус, восстановить alpha,
проверить карту и цветовое пространство. ERM и normal не обрабатывать как цвет
без отдельного теста. Не генерировать свойства материала из цвета автоматически.

## 4. Остальная полезная логика поставки

В `tech1–4` и подсказках описан зрелый рабочий процесс: общий model/material
source → отдельные НПМ/ВПМ outputs; IDs↔UDIM; UV Slicer/Auto Slicer;
Unwrap to Atlas/Windows; texel density/padding; конвертация материалов;
UCX Make Ground/Form, Triangulate, Check, Rename; Export LowPoly/HighPoly;
GeoJSON и упаковка. Это **описания возможностей**, а не проверенные API.

Особенно полезны `tooltips_UDIMs.ini:76,100,116` (edge padding, прозрачность,
грани в нескольких UDIM), `tooltips_UCX.ini:21–25` (разные проверки и изменение
зазоров). Подсказка UCX прямо различает внешний checker и встроенный метод.
Не объединять их результаты в один недоказанный статус «UCX проверен».

Готовые внешние зависимости: ImageMagick 7.1.2-0, 7z23.01,
FbxFormatConverter, normalmap, pngquant. Имеются `rules1–5.csv`, адресные/ОМКТЭ
справочники, RAL и московская подложка `.max`. Они инвентаризированы, но полнота,
дата актуальности справочников и соответствие правилам PDF2026 не установлены.
CSV и подложка не являются основанием для выдуманных координат/материалов.
Три `fbx_light_*` — кандидаты образцов для изучения, не утверждённые export presets.

Не переносить как норму предложения GeoAGR об алгоритме UV, шагах сетки,
получении каналов из diffuse или составе промежуточных объектов.
Утверждённый MaterialRegistry и трассировка к исходному PDF остаются в ядре.

## 5. Порядок интеграции и границы готовности

1. INT-001 (SINTEZ native findings → V-code/PDF) остаётся следующим этапом.
   Добавить формат native findings для `ucx_check`, сохранив его узкое покрытие.
2. В INT-006 сначала использовать этот CLI как контрольную реализацию
   пересечений; добавить отдельные проверки containment, convexity и coverage.
3. В INT-003 оценить `uvdilate` только после защиты alpha/радиуса/островов.
   Текущий собственный padding не заменять до сравнительных тестов.
4. DLL: восстановить packing/index conventions и значения p1–p5 из разрешённых
   источников или кода вызова, затем отдельный синтетический worker.
5. UI GeoAGR испытывать в изолированной Max-сцене после выбора сессии/PID.
   Clipboard `execute` не делать production-протоколом агента.

Это кандидаты операций Skills, а не установленные специализированные Skills.
Новых пустых `SKILL.md` нет. Доказана готовность двух диагностических harness;
production skills `ucx-validate`, `atlas-padding`, `geometry-repair` ещё **prototype**.
Готовность общей DCC-интеграции и пилота на реальном ОКС остаётся **нет**.

Вопросы для следующего этапа: является ли папка13.63 рабочей версией команды;
есть ли исходники/API или контакт автора для смысла DLL-параметров; какие права
есть на перенос/изменение компонентов. Ответы не нужны для хранения этих
метаданных и дальнейших независимых synthetic проверок.

## 6. Воспроизведение

Из корня репозитория, локальный .NET SDK10 и существующая Python venv:

```powershell
dotnet build tools/assembly_inventory -o tmp/geoagr-inspector --configfile tools/assembly_inventory/NuGet.Config
$g = 'C:\Users\artsafro\Desktop\zavod\GeoAGR13.63\GeoScripts'
dotnet tmp/geoagr-inspector/assembly_inventory.dll "$g\DelaunayCore.dll" "$g\FastFaceFinder.dll" "$g\moveall.dll" "$g\GeoAGR.exe"
.venv\Scripts\python.exe tools/probe_geoagr_ucx.py --exe "$g\ucx_check.exe" --out tmp/ucx-new-probe.json
.venv\Scripts\python.exe tools/probe_geoagr_uvdilate.py --exe "$g\uvdilate.exe" --out tmp/uvdilate-new-probe.json
```

Диагностики допускают только проверенный SHA-256 EXE, создают собственные
временные входы, ставят timeout и запрещают перезапись существующего JSON-отчёта.
Не передают рабочие проекты и не запускают GeoAGR/Max. Политика копирования:
бинарники, исходники поставки и восстановленный proprietary code в Git не входят.
Все 59 обследованных файлов после тестов имеют исходные хеши.

Context7 в этом продолжении не был доступен среди callable tools; в предыдущем
аудите возвращал Invalid API key. Для metadata API использована официальная
документация Microsoft, локальная сборка и фактическое чтение трёх DLL/native EXE.
