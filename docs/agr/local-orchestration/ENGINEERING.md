# Инженерные практики для локального harness AGR

Текущий приоритет после уточнения пользователя — постоянное поведение Codex,
затем визуальное наблюдение. Глобальные route/loop/engineering/review procedures,
сопоставление **всех** переданных источников и проверка активации находятся в
`tools/codex_workflow/README.md`, `SOURCE_MAP.md`, `QA.md`. `agr-task-route`
подключает общий цикл к профилям AGR. RunRecord/AdapterReport и обязательные
геометрические, native/visual/manual gates остаются действующими контрактами.
Панель ниже описывает уже выполненный этап; её развитие отложено и не является
следующим шагом внедрения этих практик в Codex.

Дата сопоставления: 03.10.2026. Этот документ связывает шесть изученных роликов
с существующим проектом. Он дополняет `AGENT_WORKFLOW.md` и RunRecord;
порядок задачи, нормы и журнал выполнения остаются в своих текущих файлах.

## Границы модулей вместо широкого рефакторинга

Глубина модуля — сколько сложности он скрывает за удобным интерфейсом.
Количество строк и файлов само по себе её не определяет.

| Существующая граница | Что скрывает | Что менять сейчас |
|---|---|---|
| `RunRecord` в `src/dt_ai/core/run_record.py` | Хеши входов, attempts, locks, subprocess receipts, timeout, stop по повторной причине и cache reuse. | Сохранить реализацию исполнения. Не дублировать ledger другим loop. |
| `AdapterReport` в `src/dt_ai/core/adapter_report.py` | Форму evidence envelope и компактный summary. | Сохранить контракт. Его валидация проверяет форму, не существование файлов и не истинность native claims. |
| `inspect_run` в `src/dt_ai/core/run_inspection.py` | Привязку manifest к ledger, текущие хеши файлов, состояния этапов, pending gates и безопасную рекомендацию. | Добавлен один read-only интерфейс, используемый `tools/harness_status.py`. Он не является runner или сертификатом сдачи. |
| `tools/run_profile_pilot.py` | Последовательность конкретного NPM transfer Обр22. | Оставить кейс-специфичным. Параметризация требует другого представительного объекта и соответствующего native QA. |
| Geometry core → DCC adapters → job/config | Вычисления, доступ к приложению и данные объекта разделены по обязанностям. | Менять лишь обнаруженную связь, мешающую конкретной задаче; не переносить DCC-вызовы в чистое ядро. |

В плане кодовой задачи: вход/выход модуля, его ответственность, ошибка/стоп,
что должно быть видно вызывающему коду, тест поведения на границе. Небольшая
правка не требует нового PRD. Уточнение («grill») нужно для значимых неизвестных,
а не как обязательный длинный опрос пользователя.

## Общий словарь и контракт свежего контекста

- **Profile** — требуемый результат по стандартам: НПМ-ОКС, ВПМ-ОКС или территория.
- **Operation/stage** — ограниченная работа: inspect, export, readback и т. п.
- **Run** — журнал одной задачи и её точного fingerprint; **attempt** — попытка с новыми выходами.
- **Produced** — инструмент записал выход; **verified** — сохранена проверка этапа.
- **Uncertain** — running есть в журнале, но живой процесс здесь не подтверждён.
- **Acceptance/delivery** — соответствие исходной цели и всем нужным воротам;
  эти статусы не выводятся из exit0, produced или verified.

При делегировании используй контракт из `AGENT_WORKFLOW.md`: цель/приёмка,
профиль и операция, exact входы и код, разрешённые ресурсы/владелец, зависимости,
выходы, проверки, стоп и следующий шаг. Передавай ссылки на нужные документы
и только релевантный контекст. Возврат содержит реальные файлы, команды/результаты,
evidence, ограничения и next action. После compaction/restart перечитай сохранённое.

Это протокол передачи, а не обещание автоматической очистки памяти, переобучения
модели или запуска новых процессов. Исполнитель и его права проверяются отдельно.
Локальные приложения и аппаратные ресурсы остаются локальными.

## Skills и команды

Проектные skills находятся в `.agents/skills/`:

| Skill | Когда применять | Проверяемый результат |
|---|---|---|
| `$agr-task-route` | Новая многоэтапная задача или изменение harness. | Выбранный маршрут, сохранённый ограниченный контракт, подходящий инструмент. |
| `$agr-run-evidence` | Возобновление или проверка сохранённого этапа. | JSON проверки фактических файлов и рекомендация без повторного исполнения. |
| `$agr-experience-transfer` | Повторение похожего кейса или решение об обобщении. | Сопоставление входов, доказанная область и требуемый второй кейс. |

Пользователь может ставить цель обычным языком. Явные вызовы выше полезны для
проверки маршрута; названия skills не превращаются в новые команды исполнения.
Геометрические и UV процедуры берутся из действующих норм и доступного доменного
`agr-vpm-npm`, а не дублируются здесь.

Codex документирует обнаружение `.agents/skills` от текущей папки до корня
репозитория. [Официальные правила skills](https://learn.chatgpt.com/docs/build-skills).
Новые custom prompts создавать не нужно: официальная документация рекомендует
skills вместо них. [Custom prompts](https://learn.chatgpt.com/docs/custom-prompts).
Проверка discovery в Codex относится к Codex; видимость в Cursor проверяется
в самом Cursor перед использованием. Один новый список YAML не доказывает вызов.

Из корня checkout, доступным проектным Python:

```text
python tools/harness_status.py --run <run-directory> --manifest <attempt/input-manifest.json>
python tools/harness_status.py --run <run-directory> --manifest <input-manifest.json> --report <report.json> --required-check <id>
```

`--required-check` повторяется для обязательных gate ID из задания. Инспектор
требует manifest в данном run и доказательства входов в формате существующего
pilot runner. Не создаёт manifest задним числом. Report, если передан, тоже должен
быть внутри run. Указанные в нём claims не считаются доказанными автоматически.

Exit 0: обнаруженных ошибок целостности нет; незакрытые gates ещё возможны.
Exit 1: файл изменён/отсутствует или нарушена evidence binding. Exit 2: ввод
не соответствует контракту либо не читается. В JSON всегда `delivery_passed=false`.
Команда не запускает DCC, не снимает locks и не доказывает живой PID.

## Визуальное наблюдение за задачей

Локальная панель `tools/agent_monitor/` соединяет read-only инспектор RunRecord
с явно подключёнными JSONL-потоками Codex. Она показывает этапы, текущую целостность
файлов, незакрытые проверки, сохранённые артефакты и рекомендацию следующего шага.
Лента выбранного потока содержит наблюдаемые вызовы, результаты, сообщения
ведущего и события делегирования; доступны фильтры и раскрытие подробностей.

Запуск и контракт config: [tools/agent_monitor/README.md](../../../tools/agent_monitor/README.md).
Все пути регистрируются локально при запуске. UI не запускает агентов, не меняет
журналы и не принимает произвольную команду или путь через HTTP. Источник событий
явно указан; текущий чат и журнал модели не считаются одним исполнителем.
Форк отображается только при наличии соответствующих metadata, а пропущенные
дочерние журналы автоматически не выдумываются и не обнаруживаются.

Проверка файлов обновляется примерно раз в 15 секунд при открытой панели,
лента — раз в 2 секунды. Ошибка новой проверки заменяет старый успешный результат.
При потере HTTP-связи сохранённый снимок получает предупреждение о давности.
Интерфейс не подтверждает живой PID, native QA, пользовательскую приёмку или
полный delivery. Исходный report и supplemental reviews не объединяются скрыто.

## Что требует отдельного следующего проекта

Автоматический fresh-agent scheduler, модель Jev, управление агентами из
визуальной панели и универсальный NPM/VPM runner требуют своих контрактов и
проверок. Приоритет определяется измеримой проблемой, а не наличием технологии
в ролике. Typed route/schema ограничивает форму решения, но не доказывает его
правильность и не заменяет права на действие.

Один mutator на DCC-сцену, узкие независимые поручения и отдельная проверка
достаточны для текущего цикла. Широкий swarm полезен только при независимых
ресурсах и ясном контракте; worktree не изолирует сцену, порт или общий экспорт.

Настройка проверяется файловыми regression fixtures, негативными примерами,
независимым forward-test skills и текущим discovery. Реальные native gates
пилотной модели остаются в job и не закрываются этими тестами. Результаты
текущего этапа — `ENGINEERING_QA.md` рядом с этим документом.
